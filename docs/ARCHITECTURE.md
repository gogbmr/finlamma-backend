# Finlamma — Architecture

Three separate projects, built in this order:

1. `finlamma-backend` — Next.js: REST API (`/api/v1`), admin dashboard, public homepage.
2. `finlamma-market-relay` — small always-on Node service for live prices.
3. `finlamma-app` — Expo / React Native mobile app.

```
                ┌──────────────── Clerk (auth, sessions) ────────────────┐
                │                                                        │
 finlamma-app ──┼── HTTPS (Bearer Clerk token) ──► finlamma-backend ──► Supabase Postgres (Drizzle)
   (Expo)       │                                   │  │  │            Supabase Storage (S3 API)
                │                                   │  │  └─► Upstash Redis (cache, leaderboards, rate limits)
                │                                   │  └────► Inngest (jobs: news, orders, streaks, certs)
                │                                   └───────► Finnhub + India news, Anthropic, Resend,
                │                                             Expo Push, RevenueCat webhooks, PostHog, Sentry
                └── Socket.IO (Clerk token) ──► finlamma-market-relay ──► Twelve Data WebSocket
                                                        └─► writes latest prices to Upstash Redis
```

## Three separate projects
Each project is its own git repository with its own `package.json`, dependencies, `.env`,
Claude Code config, tests, CI and deployment. There is **no monorepo, no shared package and
no import or file path across projects**. They only talk over the network:

| From → To | How | Contract document |
|---|---|---|
| app → server | HTTPS REST `/api/v1` | server `docs/API_ENDPOINTS.md` (generated from `/api/openapi.json`) |
| app → relay | Socket.IO `/market` | relay `docs/API_ENDPOINTS.md` (copy kept in app as `docs/RELAY_API.md`) |
| relay → server | HTTPS (instruments, market controls; `X-Relay-Secret`) | server `docs/API_ENDPOINTS.md` |
| server ↔ relay | Upstash Redis key `px:<SYMBOL>:NSE` | both CLAUDE.md files |

- The server generates an OpenAPI 3.1 spec from its Zod schemas, commits it as
  `openapi/openapi.json`, serves it at `GET /api/openapi.json`, and renders
  `docs/API_ENDPOINTS.md` (every endpoint with request and response formats) from it.
- The app downloads the contract **over HTTP** (`pnpm api:sync`), then generates its typed
  client and its own copy of `docs/API_ENDPOINTS.md`.
- Build order: server → relay → app. Each can be built, tested and deployed alone.

## Key decisions (append new ones at the bottom, never rewrite old ones)
| # | Decision | Why |
|---|---|---|
| D1 | Clerk for auth; our own `users` table keyed by `clerk_user_id`, filled by Clerk webhooks | Identity is hosted; all app data stays in our DB |
| D2 | Staff permissions live in our DB (`roles`, `permissions`, `role_permissions`), not Clerk | Portable, auditable, fine-grained |
| D2a | Two separate Clerk applications (staff vs. consumer), never one. `clerkMiddleware()`/`auth()`/`<ClerkProvider>` (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`/`CLERK_SECRET_KEY`) are bound only to the STAFF app, since staff are the only ones who ever sign in through a browser on this domain. The mobile app's users are a separate CONSUMER Clerk app (`CONSUMER_CLERK_PUBLISHABLE_KEY`/`CONSUMER_CLERK_SECRET_KEY`), verified directly in `requireUser()` via `@clerk/backend`'s `authenticateRequest()` against a Bearer token — this never touches `clerkMiddleware()`/`auth()` at all | Exactly one Clerk instance ever manages a session cookie on this domain, so there's no handshake/redirect conflict between two instances; kid accounts and staff identities stay fully separated |
| D3 | Drizzle over plain Postgres; no Supabase-only features in core (no RLS as main access control, no Edge Functions) | Later move to AWS RDS is a connection-string change |
| D4 | File storage via S3-compatible API (`@aws-sdk/client-s3`) | Later move to AWS S3 is config only |
| D5 | Live prices: one Twelve Data WebSocket in the relay, fanned out via Socket.IO | API key never ships in the app; credits per symbol, not per user |
| D6 | Trades execute at the price the server reads from Redis, never a client-sent price | Anti-cheat |
| D7 | V Money is a double-entry-style ledger; balances are derived | Full audit trail |
| D8 | Money and prices are integers (V Money units; prices in paise) | No float errors |
| D9 | Timestamps stored in UTC; business rules (streak days, market hours) use Asia/Kolkata | Correct day boundaries |
| D10 | Ad-free status via RevenueCat webhook → `entitlements` table | Razorpay can be added later as another source |
| D11 | News from Finnhub (global) + one India-focused source; AI drafts, humans publish | Coverage + editorial control |
| D12 | Activity logs are append-only; no update/delete, even for super admin | Trustworthy audit |
| D13 | `src/db/client.ts`'s postgres.js pool uses `max: 2` (not `max: 1`), plus `connect_timeout`/`idle_timeout`/`connection.statement_timeout` | **Incident**: with `max: 1`, two queries issued concurrently from one request (e.g. `Promise.all([db.select()..., db.select()...])`) hung *forever* against Supabase's transaction pooler (port 6543) - no error, and `statement_timeout` didn't catch it either, because Postgres itself never saw a problem. Root cause: postgres.js pipelines concurrent queries onto one logical connection, assuming a continuous single backend; Supavisor's transaction mode can reassign the real backend between individual statements, so the client waits forever on a response that was framed for a connection the pooler already moved on from. Confirmed by direct comparison: the same concurrent pair resolved in 50ms over the direct/session connection (no pooler) and in 285ms over the transaction pooler at `max: 2`, but hung indefinitely over the transaction pooler at `max: 1`. `max: 2` gives an accidental concurrent pair its own connection each, avoiding the single-connection pipelining path entirely. The timeouts are separate defense-in-depth, for a connection Supavisor silently drops while this module-scope client sits idle between warm Vercel invocations. Regression-guarded by `src/db/client.test.ts`; reproducible on demand via `pnpm db:verify-pool` against the real database. **Correction (2026-10-06, see D72): this only covers a concurrent PAIR.** A request issuing three or more truly concurrent queries (not two) hits the identical hang at `max: 2` - confirmed as the root cause of a real production incident, not just a theoretical gap. |
| D14 | Staff join by email invite (Clerk's Invitation API, `publicMetadata` carrying the role id), not by pasting a Clerk user ID. A separate STAFF-app webhook (`/api/webhooks/clerk-staff`, its own `STAFF_CLERK_WEBHOOK_SIGNING_SECRET`) creates the `staff_members` row on `user.created` once they accept, and deactivates it on `user.deleted`. No "pending invite" row is stored in our DB - Clerk's own invitation record is the only pending state | Self-service onboarding without ever exposing a raw Clerk user ID in the UI; deleting someone in the Clerk dashboard also revokes admin access here automatically |
| D15 | A parent's withdraw-consent token (`consent_records.withdraw_token_hash`) never expires - unlike the 7-day consent token, it has no `expires_at` and no lifetime check in `src/server/onboarding/service.ts` | India's DPDP Act requires withdrawing consent to be **as easy as giving it** - an expiring withdraw link would make revocation harder than the always-available consent link, working against that requirement. The token also stays dead-safe if leaked: it can only ever flip a `consented` row to `withdrawn` (never grants access or reveals data - see `withdrawConsentRecord`'s `WHERE status = 'consented'` guard), and a parent who withdraws by mistake can simply re-consent, minting a fresh withdraw token that supersedes the old one in place (`consent_records` is one row per user - confirming overwrites `withdraw_token_hash` unconditionally, so a leaked or old link can never revoke a *newer* consent). Net: a leaked withdraw link is low-harm, so trading off "could theoretically be replayed forever" against "must always work for as long as consent is in effect" favors never expiring it. |
| D16 | Every mutation on the public parental-consent/legal pages (`/consent/*`) and every staff mutation in `/admin` uses a Next.js **Server Action**, never a `/api/v1` REST route - e.g. `confirmParentConsentAction`/`declineParentConsentAction`/`withdrawParentConsentAction`/`approveReapprovalAction`/`declineReapprovalAction` in `src/app/consent/actions.ts`, and `saveLegalDraftAction`/`publishLegalDocumentAction` in `src/app/admin/(dashboard)/legal/actions.ts`. `/api/v1` exists for the mobile app's OpenAPI contract; neither a parent (no Finlamma account to authenticate an API call with) nor a staff member driving the admin UI is an OpenAPI/mobile-app consumer of that contract | This decision was made during Phase 2a but never recorded here until a `/phase-audit 2a` run found `docs/FEATURE_MAP.md`'s API column for the consent/legal rows still describing REST routes (e.g. `POST /api/v1/parent-consent/confirm`) that were never built - documenting it here is what keeps that kind of drift from recurring silently |
| D17 | Phase 2b's lesson/quiz-answer endpoints compute XP (speed bonus, combo, fever mode, per LF-12/LF-22) and store it on `quiz_attempts`/`question_answers`, but **never write to `xp_events` or `vmoney_ledger`** - those tables don't exist until Phase 3. The stored numbers are a display-only preview (what the report card shows), not a credited amount. `quiz_attempts` also stores an `attempt_number` and `is_first_pass` flag per (user, lesson) so that when Phase 3 wires up real crediting, it can apply anti-farming rules and credit each lesson at most once, idempotently, without redesigning this phase's tables | Phase 3 owns the ledger; building it early would mean building `reward_rules`/`vmoney_ledger`/anti-farming logic out of order. Recording the attempt number now, while the scoring code is fresh, is cheaper than reconstructing "was this the user's first clean attempt" later from attempt history alone |
| D18 | Checkpoint 4a/4b's `lessons.content` can reference a question by id (an in-video pop-quiz cue, a quiz/boss_quiz/role_play question list) before the `questions` table exists (Checkpoint 5). Those references are stored as plain UUID-shaped strings; the Checkpoint 4 publish gate validates they're **well-formed UUIDs only** - not that a matching row exists, not that it's published, since `questions` doesn't exist yet to check against. **Checkpoint 5 must close this gap**: once `questions` exists, the lesson publish gate (`publishLesson` in `src/server/lessons/service.ts`) gets a mandatory added check that rejects publishing with a dangling (no matching row) or unpublished-question reference, naming the missing/unpublished reference the same way the mentor/world completeness gates name missing translation fields | Pulling `questions` into 4a to make this checkable now would mean building a meaningful slice of Checkpoint 5's format/payload/answer schemas out of order, just to support a validation that has no real content to validate yet anyway (nobody can author a real question before Checkpoint 5 ships question authoring). Recording the gap explicitly here, rather than leaving it implicit, is what keeps Checkpoint 5 from shipping the `questions` table without also closing the loop back to lesson publishing - the same reasoning as D17 |
| D19 | A `doubt_zone` lesson's content stores `mentorKey` - which mentor persona the scripted Q&A was actually written for - fixed at authoring time, never derived from the world's current mentor. If a world's mentor is later changed (only possible while the world is a draft, which - per the world<->lesson publish dependency, Checkpoint 3/4a - requires every published lesson under it, including any doubt_zone ones, to already be unpublished first), the admin lesson editor compares the stored `mentorKey` against the world's current mentor and shows a warning banner on that lesson ("written for X, world's mentor is now Y - review before publishing") until a staff member either rewrites the script or the mentor is changed back. **No new table, column or migration** - it's a computed comparison in the editor UI, not a persisted "flagged for review" state | Simplest safe option that still surfaces the staleness where staff will actually see it (the editor, right before they'd publish). A persisted per-lesson review-flag column was considered and rejected for v1 - it adds a migration and an admin filter view for a staleness window that can only ever open while the world is already mid-edit as a draft (see the forced unpublish-lessons-first chain above), so the blast radius is small and staff are already in the editor at exactly the moment the warning needs to be seen |
| D20 | **Fixing already-PUBLISHED content** (a typo, or a wrong correct answer) is a direct "hotfix" edit on the live row, not a pending-revision-for-approval table. Scoped only to `mentors`/`worlds`/`questions` - the three types where unpublish is ever actually blocked by a child reference (mentor<->world, world<->lesson, question<->lesson - see D18/Checkpoint 3/4a/5b's reverse-reference guards) - and only to the fields that are pure content, not structure: mentor `name`/`bio`, world `title`/`tagline`, question `prompt`/`explanation`/`payload`/`answer`. `lessons` gets no hotfix mechanism: nothing ever blocks unpublishing a lesson, so the existing unpublish -> edit draft -> republish cycle already works for a lesson typo, brief unavailability during that cycle being an acceptable trade-off. A hotfix requires the domain's `.publish` permission (not `.manage` - same trust bar as publishing itself, since it changes what's live with no draft review step), re-runs the same structural/bounds/translation-completeness checks publish itself uses, and is logged (`mentor.hotfixed`/`world.hotfixed`/`question.hotfixed`). `questions` additionally gets a `revision` integer column, bumped on every hotfix that changes `payload`/`answer` (never on a draft edit or on publish itself) - Checkpoint 5b's `question_answers` stamps this value onto every graded answer, so it's always knowable which revision of a question a historical `quiz_attempt` was actually graded against, without ever retroactively re-grading a past attempt when a later hotfix changes the answer key | A pending-revision-for-approval table (draft the fix, have a second publisher approve and swap it in) was considered and rejected for v1: it's a second full review workflow layered on top of the one that already exists (draft -> publish), doubling the surface for what's supposed to be a same-day typo/wrong-answer fix, for problems (mentor/world/question circularly blocked from unpublishing) that a direct, permission-gated, logged, re-validated edit already solves safely. Scoping to only the three blocked types (not lessons) and only content fields (not structure) keeps the mechanism from becoming a second, parallel edit path for everything |
| D21 | **Checkpoint 5b's lesson-quiz answering/scoring** (`quiz_attempts`, `question_answers`, `POST /api/v1/lessons/{id}/steps/{n}/serve`, `POST .../answer`) implements every anti-cheat rule as a server-side invariant, not a client-trust convention: (1) **server-timed** - `question_answers.servedAt` is stamped by `serveStep` itself, and grading's elapsed time is always `now - servedAt` in `src/server/quiz-attempts/service.ts`, never a client-reported duration; a `LATENCY_ALLOWANCE_MS` (300ms, `src/server/quiz-attempts/scoring.ts`) grace period is subtracted before comparing against the timer, covering network round-trip, not slow answering. (2) **One answer per question per attempt, idempotent** - `question_answers` has a unique `(attempt_id, step_index)` index and `gradeQuestionAnswer` only ever updates a row where `answered_at IS NULL`; a resubmit for an already-answered step returns the exact stored result (including `timedOut`/`speedBonusAwarded`/`feverActive`, stored as columns specifically so a replay is never inconsistent with the original grading even if `settings_kv` changed since), no re-scoring, no double XP. (3) **No skip-ahead** - `serveStep` only creates a new step's row when the immediately preceding step exists and is answered (or this is step 1); `submitAnswer` only grades a step that has a served-and-unanswered row. (4) **No answer leak** - `ServeStepResponseSchema` has no answer/explanation field at all; `SubmitAnswerResponseSchema` reveals `correctAnswer`/`explanation` only for the one question just graded, only after grading. (5) **Scoring constants are `settings_kv`-driven** (`lesson_flow_scoring` key, `src/server/settings`), editable only via the `settings.manage` permission - seeded to `super_admin` alone, unlike every content permission which other roles also hold - and every change is logged with before/after values. (6) **XP is a preview only** (D17) - `quiz_attempts.total_xp_preview`/`question_answers.xp_awarded_preview` are computed and stored, `attempt_number`/`is_first_pass` are stamped on attempt creation, but nothing is ever written to `xp_events`/`vmoney_ledger` (those tables don't exist yet - Phase 3's concern) | Every rule is enforced by a DB constraint, a WHERE-clause guard, or a value computed purely server-side, rather than "the client is expected to behave" - the whole point of an anti-cheat design is that it holds even against a hostile client, and a convention documented only in a comment doesn't hold under that adversarial model. The `timedOut`/`speedBonusAwarded`/`feverActive` columns (not just recomputing them on replay) specifically close a subtle gap: without them, a resubmit's response could silently drift from the original grading if an admin tuned scoring settings in between, which would look like a bug to the learner even though `xpAwardedPreview`/`isCorrect` themselves were correctly held constant |
| D22 | **Revision recoverability and mid-flight-fix safety, corrects D21's original mechanism**: D21 shipped storing `questions.revision` on `question_answers` at GRADING time, which had two gaps a testing pass caught before any real learner used it - (1) `questions.revision` is only ever the CURRENT value; once a hotfix (D20) changes it, the exact prior payload/answer is gone, so a stored revision NUMBER alone pointed at nothing recoverable, and (2) grading read the LIVE `questions` row, so a hotfix landing between serve and answer would silently regrade an in-flight answer against the NEW answer key, not the one the learner actually saw. Fixed by: a new `question_revisions` table, a full content snapshot (`prompt`/`explanation`/`payload`/`answer`) written atomically every time `questions`' live content changes - every publish (`publishQuestionRow`, now bumping `revision` from a fresh draft's `0` to `1`, not defaulting straight to `1`) and every hotfix (`hotfixQuestionRow`) - so every value `revision` ever takes has a matching, permanent snapshot; and `question_answers.servedRevision` (same underlying `question_revision` DB column as before, now `NOT NULL`), captured ONCE at `serveStep` time from the question's revision at that exact moment, never re-derived later. `submitAnswer` now grades against `getQuestionRevision(questionId, row.servedRevision)` - the snapshot - never the live `questions` row; `question.format` is still read live since format is immutable and never changes via hotfix. An idempotent replay (D21) also rebuilds `correctAnswer`/`explanation` from this same snapshot, so a resubmit stays consistent with the original grading even years after a dozen subsequent hotfixes | The whole point of D20's hotfix mechanism is that content changes under a *live*, in-use question - D21 built the anti-cheat/idempotency half of that correctly but didn't carry the "which content" question all the way through. Snapshotting on every live-content change (not just hotfixes) is what makes `servedRevision` a real, permanent pointer rather than a number that happens to be meaningless the moment anyone fixes a typo. Capturing the revision at SERVE time (not answer time) is the one-line fix that actually closes the mid-flight race - anything computed later than serve is by definition vulnerable to a hotfix racing it |
| D23 | **Checkpoint 6: sequential world unlock, and its knock-on effect on unpublishing a lesson.** A new `lesson_progress` table (one row per `(user, lesson)`, `in_progress`/`completed`) is written entirely as a byproduct of the Checkpoint 5b quiz-attempts flow - `serveStep` starts it on a lesson's first-ever attempt, `submitAnswer` completes it once the attempt finishes - so today it only ever gets a row for a lesson kind that goes through `quiz_attempts` (video/quiz/boss_quiz/role_play, i.e. every kind with at least one graded step). `story`/`doubt_zone` lessons have no graded steps and no other "mark as done" endpoint yet, so they never get a row - a known, explicit gap, not a bug: nothing can be "in progress" on a lesson kind with no interaction endpoint at all. `GET /api/v1/worlds` (`getPublicWorlds(userId)`) now computes each world's `locked` field from this: the first (lowest-order) published world is always unlocked; every other world unlocks once the PREVIOUS world's `boss_quiz` lesson has a `completed` `lesson_progress` row for this user - sequential only, never an XP/level gate. Because a Boss Quiz is now load-bearing for every later world's unlock, **unpublishing one is a hard, unconditional block** (`unpublishLesson` throws `CONFLICT` for `kind === "boss_quiz"`, full stop - not conditional on whether a later world exists) - pulling it would both 404 a learner mid-attempt and permanently strand every world after it for every learner who hasn't reached it yet. For every OTHER lesson kind, unpublishing remains allowed, but `getLessonEditorData` now also returns each lesson's `inProgressLearnerCount` (`lesson_progress` rows with status `in_progress`), and the admin lesson editor uses it for a client-side `window.confirm()` warning before unpublishing - the same "computed from data already loaded, no dedicated warning endpoint" pattern as D19's mentor-change warning, a soft warning rather than a server-side block. The Boss Quiz block reopens the exact circular problem D20 solved for mentors/worlds/questions (an unpublish-blocked, still-live piece of content with no fix path), so **lessons now get their own D20-shaped hotfix**: `hotfixLesson`, gated on `lesson.publish`, editing `title`/`blurb`/`content` (not `worldId`/`chapter`/`step`/`kind`, which stay structural/draft-only) directly on a published lesson, re-running the exact publish-time checks (translation completeness, video cue timing, and D18's question-reference check) - this is the ONLY fix path for a boss_quiz lesson now, and the lower-disruption option `getLessonEditorData`'s warning steers staff toward for any other lesson with learners mid-way through it | A `boss_quiz` lesson is structurally different from every other lesson: it's not just content a learner reads, it's a gate other content (every later world) depends on, so "unconditional block, no exceptions" is the correct rule even though it's stricter than D20's mentor/world/question blocks (which are only conditional on an actual live reference existing right now). Reusing `quiz_attempts`/`question_answers` as `lesson_progress`'s only writer - rather than also building generic "mark as started/done" endpoints for story/doubt_zone in this checkpoint - keeps the scope to what was actually asked (world unlock + the unpublish-impact warning) instead of building a bigger progress-tracking feature no endpoint yet needs; the gap is recorded here explicitly (not silently) precisely so it isn't forgotten when story/doubt_zone completion tracking is eventually built |
| D24 | **World unlock requires PASSING the Boss Quiz, not just completing it (refines D23), plus two content-completeness guards: a `GET /api/v1/health` warning and a world-publish-time block.** `quiz_attempts` gained `accuracyPct` (0-100, correct steps / total steps), computed and stored once at attempt completion (`src/server/quiz-attempts/service.ts`'s `submitAnswer`) from the attempt's own graded `question_answers` rows. A new admin-editable `settings_kv.lesson_flow_scoring.bossQuizPassMarkPct` (default 60%, edited only via `settings.manage` - `super_admin` only - and logged, same as every other Lesson Flow scoring constant) is the threshold. `src/server/worlds/service.ts`'s `getPublicWorlds` now unlocks a world once the PREVIOUS world's Boss Quiz has at least one COMPLETED `quiz_attempts` row with `accuracyPct >= bossQuizPassMarkPct` (`getWorldIdsWithPassedBossQuiz`, `src/server/quiz-attempts/repo.ts` - this replaces D23's original `lesson_progress`-based `getWorldIdsWithCompletedBossQuiz`, which is deleted; `lesson_progress` keeps its other role, the admin unpublish-in-progress-learner warning, unaffected by this change). Failing doesn't lock anything - a learner simply starts a fresh attempt (`serveStep`'s existing "no attempt exists -> create a new one" path already handles this with no code change), and ANY one of their attempts (not just the most recent or the first) passing is enough to clear the world, so a later successful retry after an earlier failure still unlocks it. Separately: `GET /api/v1/health` gained a non-fatal `worldsMissingBossQuiz` warning (published worlds with no published `boss_quiz` lesson - the unlock gate above can never clear past one for anyone). And `publishWorld` now blocks publishing a world unless it already has at least one `boss_quiz`-kind lesson **of any status, a draft is enough** (`hasBossQuizLesson`, `src/server/lessons/repo.ts`) - going forward only, never retroactively against an already-published world (that's what the health-check warning is for; the 7 existing seeded worlds were deliberately left published with zero lessons at all - see `docs/STATUS.md`) | "Completed" and "passed" are genuinely different things for a Boss Quiz specifically (every other lesson kind has no pass/fail concept at all, just "did you finish it," which is exactly what `lesson_progress` still tracks for them) - gating world progression on mere completion would let a learner unlock World 2 by answering every Boss Quiz question wrong, which defeats the purpose of a "boss" checkpoint. Storing `accuracyPct` once, at completion, rather than computing it on every unlock check, keeps the unlock query a single indexed lookup instead of re-aggregating `question_answers` for every attempt on every `GET /api/v1/worlds` call. The publish-time block can only require a DRAFT boss_quiz lesson, never a published one: `publishLesson` already requires its world to be published first (Checkpoint 4a), so a world's very first-ever publish can structurally never have a published boss_quiz lesson yet - requiring one at world-publish time would make it impossible to ever publish a new world at all. Requiring a draft is the closest enforceable version of "don't publish a world with no boss quiz plan," and staff publish the lesson itself right after the world |
| D25 | **Worlds and mentors are fully data-driven, unbounded content types - no fixed count, names, keys or mentor-world ranges anywhere in code.** Staff decide how many worlds exist (5, 7, 10, 20, any number) and how many mentors exist, through the admin editors; the 7-world/3-mentor (Baby/Father/Grandpa Lamma) prototype set is seed data only (`scripts/seed-worlds.ts`/`scripts/seed-mentors.ts`), fully editable, reorderable and (once empty of lessons) deletable. A mentor's assignment to a world lives **only** on `worlds.mentorId` (a real FK, chosen per world in the admin World editor) - the `mentors` table's old `worldRangeStart`/`worldRangeEnd` columns are removed (migration `drizzle/0020_cynical_nomad.sql`); one mentor can cover any number of worlds, and the admin Mentor editor shows a read-only "Used by" list computed from `worlds.mentorId` (`listWorldsByMentorId`, `src/server/worlds/repo.ts`) rather than a stored range. Mentors gained a `persona` text column (free-text voice/tone notes for the Doubt Zone AI chat - internal, staff-only, never in the public `GET /api/v1/mentors` response). A world's `theme` is a staff-chosen hex color, validated (`ThemeHexSchema`, `src/server/worlds/schemas.ts`) rather than an enum of fixed prototype themes. **World deletion**: `deleteWorld` (`src/server/worlds/service.ts`) permanently removes a world only while it has zero lessons of any status (`listAllLessonsForWorld`) - since `lesson_progress` rows are keyed off a lesson, a world with no lessons structurally cannot have learner progress either, so this one check is sufficient; `deleteWorldRow` (`src/server/worlds/repo.ts`) closes the resulting gap in `order` in the same transaction, without `moveWorldToPosition`'s negative-sentinel trick (a delete only ever shifts values down into a slot the delete, or the previous shift, just vacated). **Trading's unlock is by world POSITION, never a specific world's id or name**: a new admin-editable `settings_kv.lesson_flow_scoring.tradingUnlockAfterWorldPosition` (default 3, i.e. the 3rd published world, `settings.manage`-gated and logged like every other Lesson Flow scoring constant) drives `isTradingUnlocked(userId)` (`src/server/worlds/service.ts`) - not consumed by any endpoint yet (Phase 4's trading domain will import it directly), but built and tested now while the world/mentor model is already in flux. If fewer published worlds exist than the configured position, trading stays locked for everyone and `GET /api/v1/health` warns (`tradingUnlockWorldMissing`) | The original schema already got the world<->mentor relationship half-right (a real `mentorId` FK on `worlds`, never a computed lookup) but layered a second, parallel "world range" concept onto `mentors` that could drift from it and structurally couldn't express "one mentor, many non-contiguous worlds" or "any number of mentors/worlds" - a request for "5 worlds, 10 worlds, 20 worlds, any number" surfaced this as a real product requirement, not a hypothetical.
